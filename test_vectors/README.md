# Test vectors for the firmware freeze detector

Generated by `python src/streaming_detector.py --export` (run from `analysis/`) from real Daphnet ankle data.
`analysis/src/streaming_detector.py` is the reference: it has been checked frame-for-frame against the
batch evaluation code on the whole dataset (35,405 frames, zero cue mismatches), and running
it in float32 changed no decisions. If your C code disagrees with these files, the C code is wrong.

## Files

Each scenario has two files.

`<name>_input.csv`: one row per sample at 64 Hz, accelerometer in **milli-g**: `ax_mg, ay_mg, az_mg`.
Feed the rows in order into a freshly reset detector.

`<name>_expected.csv`: one row per detector frame (every 32 samples, starting once 256 samples are in).

| column | meaning |
|---|---|
| `sample_index` | 0-based index of the newest input sample in this frame's window (255, 287, 319, ...) |
| `freeze_index` | freeze-band power / locomotion-band power |
| `total_power` | locomotion + freeze band power, mg² |
| `loco_power` | locomotion band power, mg² |
| `positive` | raw detector decision for this window |
| `armed` | walking gate state used for this frame |
| `cue_on` | buzzer state. **This is the column that must match.** |
| `label_freeze` | clinician's label at that sample. For information only, the detector never sees it |

| scenario | what it checks |
|---|---|
| `walk_then_freeze` | an early positive run is ignored (no walking yet), then the cue starts when walking runs into a freeze and holds for 5 s |
| `standing_still` | power stays under the threshold, nothing fires |
| `gate_blocked` | one legitimate cue, then long positive runs with no recent walking: cue must stay off |
| `long_freeze` | the cue keeps playing through a ~30 s freeze even though the walking gate lapses after 5 s |

## The algorithm, per sample

1. `mag = sqrt(ax² + ay² + az²)` in milli-g. Write it into a 256-entry ring buffer.
2. Once 256 samples are in, and then every 32 samples, compute a frame:
   1. Copy the buffer and subtract its mean. **You do not need to unroll the ring buffer into
      time order:** a circular shift only changes the phase of the FFT, and everything below uses
      magnitudes. A plain `memcpy` is enough.
   2. 256-point real FFT, no window function. Bin `k` is `k × 0.25 Hz`.
   3. `bin_power[k] = (re² + im²) × 2 / 256²`. With this scaling a sum over bins is the signal
      variance inside that band, in mg².
   4. `loco = sum(bin_power[2..11])` (0.5 to 2.75 Hz), `freeze = sum(bin_power[12..32])` (3 to 8 Hz), both inclusive.
   5. `freeze_index = freeze / max(loco, 1e-9)`, `total = loco + freeze`.
   6. `positive = freeze_index > 1.056 && total > 178`.
3. Cue state machine, once per frame (`i` = frame counter):

```
consecutive = positive ? consecutive + 1 : 0
armed = (number of true flags in walk_history) >= 2       // uses the history BEFORE this frame is added
if (cue_on)  cue_on = positive || i < hold_end            // the gate does not apply to a cue that is already playing
if (!cue_on && positive && armed && consecutive >= 2) { cue_on = true; hold_end = i + 10; }
walk_history[walk_head] = loco > 10000;  walk_head = (walk_head + 1) % 10
i++
```

`walk_history` is a 10-entry ring buffer of booleans (5 s), initialised to false.
All constants live in `DetectorParams` in `analysis/src/streaming_detector.py`.

## Comparing

- `cue_on`, `positive` and `armed` should match exactly on all four vectors.
- `freeze_index`, `total_power`, `loco_power`: allow a relative error of about 1e-3. Float32 in the
  Python reference differs from float64 by at most 1.4e-5, so anything near 1e-2 is a real bug,
  most likely FFT scaling or an off-by-one in the bin ranges.
- If the numbers are off by a constant factor, check the FFT normalisation. The reference uses an
  unnormalised forward FFT (NumPy/SciPy convention). CMSIS-DSP `arm_rfft_fast_f32` is believed to
  use the same convention and returns interleaved `[re0, im0, re1, im1, ...]`, but confirm that
  against its documentation. It also overwrites its input buffer, which is another reason to
  transform a copy.

## Easiest way to run them

Build the detector as plain C with no hardware dependencies (`detector_push(ax, ay, az)` returning
a frame struct), compile it on the laptop, and feed it these CSVs. Only move it onto the STM32
once it passes. The real sensor then only has to deliver milli-g at a steady 64 Hz.
